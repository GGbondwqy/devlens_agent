# DevLens Agent 设计文档

## 1. 定位与设计目标

一句话：**面向企业研发流程的多智能体代码协作框架**，把「分析 Issue / 审查 PR / 排查 CI 失败」
产品化为 `规划 → 证据检索 → 结论生成 → 质检（反思回路）` 的流水线。

设计目标（按优先级）：
1. **框架先行**：Agent 内核、工具系统、编排引擎、事件流完整可用，模型是可替换组件；
2. **离线可跑**：Mock 模型驱动全流程（演示/测试零成本），接真实模型只改配置；
3. **证据优先**：所有结论必须可追溯到 `file:line`，Critic 以证据充分性质检；
4. **可观测**：全链路类型化事件，CLI/SSE 双通道，落盘可回放；
5. **安全边界**：路径收敛、命令白名单、输出截断。

## 2. 分层架构

```
┌─────────────────────────────────────────────────────┐
│                接入层：CLI / FastAPI+SSE / Web        │
├─────────────────────────────────────────────────────┤
│  TaskRunner 组装层：配置→沙箱→KB→工具→模型路由→图→引擎  │
├─────────────────────────────────────────────────────┤
│  workflow 编排层：FlowEngine(状态机) + graphs(场景图)  │
├─────────────────────────────────────────────────────┤
│  core 内核层：BaseAgent(ReAct) + ContextManager      │
│               + EventBus(事件溯源)                    │
├───────────────────────┬─────────────────────────────┤
│  llm 模型层            │  tools 工具层                │
│  LLMProvider 抽象      │  ToolRegistry + Sandbox     │
│  Mock / OpenAI 兼容    │  10 个内置工具               │
│  Router(按角色路由)    │  KB(TF-IDF, 可换向量库)      │
└───────────────────────┴─────────────────────────────┘
```

依赖方向严格向下：上层知道下层抽象（`LLMProvider`/`Tool`），下层不知道上层。
这保证了 Mock↔真实模型、CLI↔Web、TF-IDF↔向量库的替换都不跨层。

## 3. 核心机制

### 3.1 Agent 内核（core/agent.py）

```
while 步数未用尽:
    resp = llm.chat(messages, tools=schemas)      # Think
    if resp.tool_calls:
        messages += [assistant(tool_calls)]        # Act
        for call in resp.tool_calls:
            result = tools.execute(call.name, call.arguments)   # 沙箱内执行
            messages += [tool(result)]              # Observe（事件：TOOL_CALLED/RESULT）
        messages = context.trim(messages)           # 预算保护
    else:
        return FinalAnswer(resp.content)
return 强制收敛（max_steps）
```

- 内核不知道业务（角色知识在 `roles/specs.py` 的系统提示词与工具白名单里）；
- 内核不知道模型（`LLMProvider` 注入）；
- 角色差异全部数据化：`RoleSpec(role, system_prompt, tools 白名单, max_steps)`——最小权限原则。

### 3.2 工具系统（tools/）

每个工具 = `name + description + JSON Schema 参数 + execute()`，schema 与 OpenAI function calling
同构（导出即用）。所有执行收敛到 `ToolRegistry.execute()`：

```
未注册拦截 → required/未知参数校验 → 工具执行(异常转结构化错误) → 输出截断(max_output_chars)
```

ACI 实践（来自 SWE-agent 的教训）：
- `read_file` 输出带行号 → 模型能直接产出 file:line 引用；
- 工具输出超长一律截断并注明原始长度；
- 命令执行走白名单（git/python/pytest），拒绝即记录（`denied_commands` 审计）。

`Sandbox.resolve_in()` 把任意路径解析收敛到工作区或只读附加根内，阻断目录穿越。

### 3.3 编排引擎（workflow/engine.py）

概念映射（与 LangGraph 对照，便于迁移）：

| 本框架 | LangGraph | 说明 |
|---|---|---|
| `FlowGraph` | `StateGraph` | 节点 + 条件边 |
| `FlowNode.route` | `add_conditional_edges` | 分支函数 (state, result) → branch |
| `FlowState` | `State`（TypedDict/Pydantic） | 黑板 + 节点产出 + 回路计数，可序列化 |
| `save_checkpoint` | `MemorySaver`/`SqliteSaver` | 检查点续跑 |
| 反思回路 | critic 条件边回环 | 受 `max_reflections` 预算约束 |

为什么自研：编排语义只需「节点 + 条件边 + 受限回路 + 检查点」，自研约 200 行，完全可控、可测试、
可在面试中讲清每一步；LangGraph 的 checkpoint/人机交互等高级能力当前用不到。
（trade-off：放弃了现成的持久化后端与时间旅行调试，已在 Roadmap 列出适配层方案。）

节点钩子：
- `build_task(state)` —— 从黑板生成该角色的任务指令；
- `background(state)` —— 注入上游上下文（规划/证据清单/上游产出摘要）；
- `absorb(state, output)` —— 解析产出写黑板：`EVIDENCE | 文件 | 行号 | 引用` 行进证据池、
  Critic 的 JSON 裁决进 `last_verdict`；
- `route(state, result)` —— Critic 的 pass/revise 分支，revise 受预算约束（耗尽则带病交付并记录）。

### 3.4 上下文管理（core/context.py）

- token 粗估：CJK 按字、其余 4 字符/token（只用于预算控制，不追求精确）；
- 超预算裁剪：保留 system + 首条 user（原始任务）+ 最近 N 条；中段压缩为摘要占位；
- **摘要必须比被替换内容更小**，否则退化为「N 条消息已裁剪」计数占位（防止摘要本身爆预算）；
- 摘要函数可插拔：接真实模型后可换 LLM 层级摘要。

### 3.5 事件溯源（core/events.py）

`EventBus` 为唯一可观测通道：CLI 注册回调渲染、SSE 订阅队列、`EventSinker` 落盘
`.runs/<task_id>/events.jsonl`（支持 `devlens replay` 离线回放）。观察者异常不影响主流程。

### 3.6 多模型网关（llm/）

- `LLMRouter.for_role(role)`：mock 模式按 (角色, 场景) 绑定确定性策略；
  真实模式按 `model_map` 给不同角色分配不同模型（成本/能力分层优化的落点）；
- `OpenAICompatibleLLM`：标准 chat/completions + tools 序列化，兼容 DeepSeek/Qwen/GLM/vLLM/Ollama。
  当前为预留实现（未联调真实 Key），协议字段按官方规范编写。

### 3.7 Mock 策略设计（llm/mock_policies.py）

Mock 不是硬编码剧本：策略解析工具的**真实返回**（搜索命中、日志内容、diff 内容）决定下一步，
与真实 ReAct 同构。例如：
- Researcher 从 issue 正文抽标识符 → `search_code("def apply_discount")` → 读首个命中文件 →
  `search_docs` 知识库 → 汇总 EVIDENCE；
- Reviewer 从 `git_diff` 输出抽变更文件列表 → 逐文件 `read_file` → 按「except Exception + 相邻 pass」
  启发式判定吞异常风险；
- Critic 检查证据条数与结论结构 → JSON 裁决 → 驱动反思回路。

因此：工具系统、沙箱、日志格式、KB 的任何变化都会如实反映到最终报告——Mock 测的是**框架**，
不是台词。

### 3.8 评测 harness（eval/harness.py）

三个场景 × 五个结构断言（定位正确 / 章节完整 / 证据条数 / Critic 裁决 / 状态），
输出打分报告（`eval_report.json`）。接真实模型后，同一断言集即可度量模型效果，
也可以按 CodeRabbit 思路扩展 precision/recall 统计。

## 4. 数据流（以 Issue 场景为例）

```
ISSUE-101.json
  → TaskRunner(组装) → FlowEngine.run()
    → plan 节点（Planner 输出拆解 → blackboard.plan）
    → research 节点（search_code/read_file/search_docs → EVIDENCE 行 → blackboard.evidence）
    → analyze 节点（精读源码 → 归因报告，根因挂 file:line）
    → critic 节点（证据≥2 且有结论 → pass → END / revise → 回 research）
  → result.md + state.json(检查点) + events.jsonl(回放) + summary.json(台账)
```

## 5. 安全设计

| 威胁 | 缓解 |
|---|---|
| 目录穿越（../../etc/passwd） | `resolve_in` 强制落在工作区/只读根内 |
| 高危命令（rm/curl/...） | 白名单 + 拒绝记录审计 |
| 上下文爆炸 | 工具输出截断 + 消息裁剪 + 摘要保底 |
| 无限循环 | Agent 级 max_steps + 引擎级 max_rounds + 反思 max_reflections 三层预算 |
| LLM 异常击穿任务 | 异常转结构化 AgentResult(failed)，流程可终止可续跑 |
| 写操作误伤 | `requires_approval` 标记（接真实模型后接人工审批 hook） |
