# 开发指南（二次开发手册）

本文面向想读懂 / 改造 / 扩展 DevLens Agent 的开发者。读完你可以：
新增一个工具、新增一个角色、新增一个场景、接入真实模型、接入自己的业务仓库。

## 0. 环境准备

| 要求 | 说明 |
|---|---|
| Python ≥ 3.10 | 用了 `X \| Y` 类型语法 |
| git | 仅靶场仓库初始化与 PR 场景需要；缺失时其余功能不受影响 |
| 无需 API Key | 默认 Mock 模型全流程离线可跑 |

```bash
git clone https://github.com/GGbondwqy/devlens_agent.git
cd devlens_agent
pip install -e ".[dev]"          # 安装依赖（含 pytest）
python scripts/setup_fixtures.py # 初始化靶场仓库（git main + pr-42 分支）
python -m pytest tests/ -q       # 32 个测试，约 2 秒
python -m devlens.cli run issue --input fixtures/issues/ISSUE-101.json
```

## 1. 架构导览

```
CLI (cli.py)                Web (server/app.py, FastAPI + SSE)
      └────────────┬────────────┘
              TaskRunner (runner.py)        ← 组装入口：配置→沙箱→KB→工具→模型路由→图→引擎
                   │
      FlowEngine (workflow/engine.py)       ← 状态机驱动：节点→absorb→route→下一节点→检查点
        │            │
   FlowGraph      BaseAgent (core/agent.py) ← ReAct 循环（与业务/模型无关）
   (graphs.py)      │            │
                 LLMProvider   ToolRegistry (tools/base.py)
                 (llm/)          └─ Sandbox (tools/sandbox.py) ← 路径收敛 + 命令白名单
```

一次 `run issue` 的完整调用链：

```
cli → TaskRunner.run_task("issue", data)
    → build_graph("issue")  得到 plan→research→analyze→critic 流程图
    → FlowEngine.run()
        对每个节点：
          node.build_task(state)              # 从黑板生成任务
          agent.run(task, state.digest())     # ReAct 循环（可多次工具调用）
          node.absorb(state, output)          # 解析 EVIDENCE/裁决 → 写黑板
          branch = node.route(state, result)  # critic: pass/revise
          save_checkpoint(state)              # 可续跑
    → RunsStore.save_result() → .runs/<task_id>/{result.md,state.json,events.jsonl,summary.json}
```

## 2. 核心抽象速查

| 抽象 | 位置 | 职责 | 扩展点 |
|---|---|---|---|
| `RoleSpec` | `roles/specs.py` | 角色数据化定义：系统提示词、工具白名单、步数预算 | 加角色只需加一个 spec |
| `BaseAgent` | `core/agent.py` | ReAct 循环 + 事件发射，无业务知识 | 一般不需要动 |
| `LLMProvider` | `llm/base.py` | 模型抽象（chat(messages, tools) → LLMResponse） | 实现新后端（如 Anthropic 原生） |
| `MockPolicy` | `llm/mock.py` + `llm/mock_policies.py` | Mock 模式的确定性策略（解析工具真实返回决定下一步） | 为新角色写策略 |
| `LLMRouter` | `llm/router.py` | 按 (角色, 场景) 路由到 Provider/模型 | 真实模式改 model_map 即可 |
| `Tool` / `ToolRegistry` | `tools/base.py` | 工具声明（JSON Schema）+ 统一执行（校验/截断/异常转换） | 加工具只需实现 Tool 子类并注册 |
| `Sandbox` | `tools/sandbox.py` | 路径收敛、命令白名单、命令执行 | 调整 `settings.yaml` 的 sandbox 段 |
| `FlowGraph`/`FlowNode` | `workflow/engine.py` | 节点 + 条件边 + 钩子（build_task/background/absorb/route） | 场景 = 一张图 |
| `FlowState` | `workflow/engine.py` | 可序列化状态：黑板(evidence/plan/verdicts) + 节点产出 | 黑板字段按需加 |
| `EventBus`/`Event` | `core/events.py` | 全链路事件（订阅 = CLI 渲染 / SSE / 落盘） | 新事件类型直接加枚举 |
| `ContextManager` | `core/context.py` | token 估算 + 裁剪 + 摘要（摘要必须更小的保底） | 可换 LLM 摘要 |
| `DocKnowledgeBase` | `tools/kb_tools.py` | TF-IDF 文档检索（query → chunks，接口同向量检索） | 换 embedding 实现 |
| `RunsStore` | `memory/local.py` | 任务台账与产物持久化 | 加产物类型 |

## 3. 二次开发教程

### 3.1 新增一个工具

示例：新增「AST 符号检索」工具（列出文件里的类/函数定义，比 grep 更结构化）。

**第 1 步**：在 `devlens/tools/` 新建或追加 Tool 子类（三要素：name / description / parameters + execute）：

```python
# devlens/tools/ast_tools.py
import ast
from pathlib import Path
from typing import Any
from devlens.tools.base import Tool, ToolResult
from devlens.tools.sandbox import Sandbox

class AstSymbolsTool(Tool):
    name = "ast_symbols"
    description = "列出 Python 文件中的类与函数定义（名称 + 行号范围），适合结构化定位。"
    parameters = {
        "type": "object",
        "properties": {"path": {"type": "string", "description": "相对工作区的 .py 文件"}},
        "required": ["path"],
    }

    def __init__(self, sandbox: Sandbox) -> None:
        self.sandbox = sandbox

    def execute(self, **kwargs: Any) -> ToolResult:
        path = self.sandbox.resolve_in(str(kwargs["path"]))
        tree = ast.parse(path.read_text(encoding="utf-8"))
        lines = []
        for node in ast.walk(tree):
            if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef, ast.ClassDef)):
                lines.append(f"{node.name}  (L{node.lineno}-L{node.end_lineno})")
        return ToolResult(ok=True, output=f"{self.sandbox.relative_display(path)}:\n" + "\n".join(lines))
```

**第 2 步**：注册到 `tools/factory.py` 的 `build_default_registry()`：

```python
from devlens.tools.ast_tools import AstSymbolsTool
registry.register(AstSymbolsTool(sandbox))
```

**第 3 步**：在 `roles/specs.py` 给需要的角色加白名单（如 `RESEARCHER.tools` 增加 `"ast_symbols"`）。

完成。schema 会自动导出为 function calling 格式；接真实模型后模型即可调用它，
Mock 模式下可在策略里显式调用（见 3.2）。**记得补一个单测**（参考 `tests/test_tools.py`）。

### 3.2 新增一个角色

以「文档工程师 Documenter」为例（消费分析报告，生成对外文档）：

```python
# roles/specs.py 新增
DOCUMENTER = RoleSpec(
    role="documenter",
    name_zh="文档工程师",
    system_prompt="你是研发团队的文档工程师……输入是一份归因分析报告，输出面向新人的复盘文档……",
    tools=["search_docs"],      # 最小权限：只给需要的工具
    max_steps=4,
)
ROLE_SPECS["documenter"] = DOCUMENTER
```

- **真实模型模式**：到这里就完成了——`LLMRouter.for_role("documenter")` 会按
  `model_map`（缺省用 default 模型）接入。
- **Mock 模式**：需要给该角色配一个策略，否则落到 `EchoPolicy`（返回提示文本）。
  在 `llm/mock_policies.py` 实现 `MockPolicy`（解析消息历史 → 返回工具调用或最终文本），
  并在 `build_policy()` 加分支。
- **进图**：在 `workflow/graphs.py` 的场景图中 `add_node(FlowNode("doc", "documenter", ...))` 并连边。

### 3.3 新增一个场景（垂直业务）

以「单测生成」为例，四个文件：

1. `workflow/graphs.py` 加图定义：

```python
def build_testgen_graph(max_reflections: int) -> FlowGraph:
    g = FlowGraph(entry="plan")
    g.scenario = "testgen"
    g.add_node(FlowNode("plan", "planner", build_task=_t_plan, absorb=_absorb_plan))
    g.add_node(FlowNode("research", "researcher", build_task=_t_research_for_testgen,
                        background=_bg_plan_only, absorb=_absorb_evidence))
    g.add_node(FlowNode("develop", "developer", build_task=_t_develop,   # 新角色：写测试
                        background=_bg_for_testgen))
    g.add_node(FlowNode("critic", "critic", build_task=_t_critic,
                        background=_bg_for_report, absorb=_absorb_verdict,
                        route=make_critic_route(max_reflections)))
    g.add_edge("plan", "research"); g.add_edge("research", "develop"); g.add_edge("develop", "critic")
    g.add_edge("critic", END, branch="pass"); g.add_edge("critic", "research", branch="revise")
    return g
```

2. `runner.py`：`SUPPORTED_SCENARIOS = ("issue", "pr", "ci", "testgen")`。
3. `cli.py` 不用改（choices 引用 `SUPPORTED_SCENARIOS`）；写一份 fixture JSON（字段参照现有三个）。
4. `eval/harness.py` 加 `EvalCase` 与断言。

### 3.4 接入真实模型

```bash
export DELENS_LLM_PROVIDER=openai_compatible
export DELENS_API_KEY=sk-xxxx
# 或直接改 config/settings.yaml
```

- 任何 OpenAI 兼容端点都行：DeepSeek / Qwen(DashScope 兼容模式) / GLM / Kimi / vLLM / Ollama；
- `model_map` 支持按角色路由不同模型（如 critic 用便宜模型）；
- **联调建议**：先用 `run issue` 小场景验证；若报 tool_calls 解析错误，检查端点是否支持
  function calling（`llm/openai_compatible.py` 是唯一可能要微调的文件）；
- Mock 与真实模型跑同一条流水线，切换不改动任何业务代码。

### 3.5 接入自己的业务仓库

任务输入 JSON 的 `repo` 字段指向任意**本地** git 仓库（相对项目根）：

```json
{ "id": "MY-PR-1", "title": "...", "base": "main", "head": "feature-x", "repo": "path/to/your/repo" }
```

- 研究者/评审者的搜索、读取、git_diff 都以该仓库为工作区（沙箱隔离）；
- 知识库自动加载 `<repo>/docs/` 下的 md/txt；公司 Wiki / 历史故障库可放到 `fixtures/kb/`；
- 接 GitHub/GitLab 在线仓库（webhook → clone → 流程）是 Roadmap 方向，
  `TaskRunner.run_task()` 是推荐的集成切入点。

### 3.6 检索升级（TF-IDF → 向量库）

`DocKnowledgeBase.search(query, top_k) -> [{source, text, score}]` 是唯一约定：
实现同签名 + 同返回结构（如 embedding + PGVector），在 `tools/factory.py` 替换注入即可，
工具层与 Agent 循环零改动。

## 4. 调试与观测

| 手段 | 命令/位置 |
|---|---|
| 完整工具输出 | `python -m devlens.cli run ... -v` |
| 事件回放 | `python -m devlens.cli replay <task_id>` |
| 任务台账 | `python -m devlens.cli tasks` |
| 检查点续跑 | `python -m devlens.cli run ... --resume` |
| 产物目录 | `.runs/<task_id>/`：result.md（报告）、state.json（检查点）、events.jsonl（事件）、summary.json（元数据） |
| Web 实时流 | `python -m devlens.cli serve` → http://127.0.0.1:8000 |

常见问题：
- **Windows 控制台乱码**：CLI 已做 UTF-8 reconfigure；如仍乱码执行 `chcp 65001`；
- **PR 场景报 git 错误**：靶场仓库未初始化，执行 `python scripts/setup_fixtures.py --force`；
- **Mock 报告内容不对**：Mock 策略解析的是工具的**真实返回**，先确认工具输出（用 -v 看 TOOL_RESULT）。

## 5. 测试规范

- 所有测试**离线**（Mock 模型 + 本地 fixture），禁止依赖外网 / API Key / 真实模型；
- 用 `tests/conftest.py` 的 `fixture_repo` 夹具保证靶场仓库就绪；
- 新工具/角色/场景至少各补一条单测；改引擎行为需同步 `tests/test_workflow_engine.py`；
- `python -m devlens.cli eval` 是端到端回归闸门：三场景必须 100 分（CI 已强制）。

## 6. 配置参考（config/settings.yaml）

| 字段 | 默认 | 说明 |
|---|---|---|
| `llm.provider` | `mock` | `mock` / `openai_compatible` |
| `llm.openai_compatible.base_url` | DeepSeek | 任意 OpenAI 兼容端点 |
| `llm.openai_compatible.api_key` | 空 | 建议用环境变量 `DELENS_API_KEY` |
| `llm.openai_compatible.model_map` | default | 角色级模型路由（多模型成本优化的落点） |
| `context.max_tokens` / `keep_recent_messages` | 8000 / 8 | 上下文预算与裁剪保留窗口 |
| `sandbox.command_whitelist` | git/python/pytest | 允许执行的命令前缀 |
| `sandbox.command_timeout` / `max_output_chars` | 30 / 6000 | 命令超时（秒）/ 工具输出截断阈值 |
| `workflow.max_rounds` / `max_reflections` | 12 / 1 | 流程图总轮数上限 / 反思打回次数预算 |
| `storage.runs_dir` | `.runs` | 任务产物目录 |

环境变量优先级高于配置文件：`DELENS_LLM_PROVIDER` / `DELENS_BASE_URL` / `DELENS_API_KEY`。
